자체 호스팅 환경의 Slack 연결은 bring-your-own-app(BYO) Socket Mode 방식으로 동작합니다. 에이전트마다 전용 Slack app을 준비하고, Patchbay는 연결된 app마다 Socket Mode 연결을 엽니다. Patchbay Cloud에는 추가 설정이 필요 없습니다. 자체 호스팅 환경에서는 token 암호화 키와 멤버가 접근할 수 있는 공개 URL을 먼저 설정하세요.

이 페이지는 [Slack Bot 연동](/slack-bot-integration) 과 [채팅 연동](/channels) 의 자체 호스팅용 보충 설명입니다. 컨테이너 구성과 업그레이드는 [자체 호스팅 빠른 시작](/self-host-quickstart) 을, 변수 전체 목록은 [환경 변수](/environment-variables) 를 참조하세요.

## 자체 호스팅 Slack의 동작 방식

- Slack app 하나는 Patchbay 에이전트 하나에 대응합니다. 여러 에이전트를 연결하려면 에이전트마다 app을 만드세요.
- Bot이 Socket Mode로 Slack에 아웃바운드 연결하므로, BYO 설치에는 공개 Request URL이나 OAuth Redirect URL이 필요 없습니다.
- 각 설치는 전용 App-level Token(`xapp-`)을 가지고, 그 token으로만 인증하는 전용 Socket Mode 연결을 사용합니다. Bot token(`xoxb-`)은 `chat.postMessage` 같은 아웃바운드 Web API 호출 전용입니다.
- 인바운드 이벤트는 실제 Slack app id(`config->>'app_id'` 를 이벤트의 `api_app_id` 와 대조)로 라우팅되므로, 여러 BYO app, 즉 여러 에이전트가 하나의 Slack workspace에 공존할 수 있습니다.

관리 API는 다음 네 개뿐입니다.

- `GET /api/workspaces/{id}/slack/installations` — 설치 목록 조회(멤버도 볼 수 있음).
- `POST /api/workspaces/{id}/slack/install/byo?agent_id=…` — BYO app 연결(owner / admin). 본문: `{ "bot_token": "xoxb-…", "app_token": "xapp-…" }`.
- `DELETE /api/workspaces/{id}/slack/installations/{installationId}` — 연결 해제(owner / admin). 행은 감사 기록용으로 남고, 다시 연결하면 active로 돌아갑니다.
- `POST /api/slack/binding/redeem` — "계정 연결" 링크에서 Slack user id를 로그인한 Patchbay 사용자에게 바인딩합니다.

호스팅 전용(`PATCHBAY_SLACK_CLIENT_ID/_SECRET` 없이는 동작하지 않음):

- `POST /api/workspaces/{id}/slack/install/managed` — 매니지드 OAuth 승인을 시작합니다(owner/admin). Body: `{ "redirect_url": "…" }`.
- `GET /api/integrations/slack/oauth/callback` — Slack 리디렉션용 공개 엔드포인트. 일회용 state를 소비하고 code를 교환한 뒤 바인딩된 redirect URL로 302합니다.
- `POST /api/integrations/slack/events` — 매니지드 Events API용 공개 webhook(HMAC 서명, app + team으로 테넌트 라우팅). 매니지드 설치에는 Socket Mode 연결이 없으며, 이것이 유일한 인바운드입니다. Supervisor는 다이얼 없이 슬롯을 유지합니다.

## 1. BYO Socket Mode 배포

1. `PATCHBAY_SLACK_SECRET_KEY` 를 설정하고([자격 증명 취급](#4-자격-증명-취급) 참조) 백엔드를 다시 시작합니다. 이 키가 없으면 Slack 연동 전체가 비활성화됩니다.
2. [Slack Bot 연동](/slack-bot-integration) 의 manifest로 에이전트마다 Slack app을 만들고 Slack workspace에 설치한 뒤, `xoxb-` Bot token과 `xapp-` App-level Token(`connections:write` scope)을 복사합니다.
3. Patchbay에서 해당 에이전트의 **연동** 페이지를 열어 두 token을 붙여넣거나, `POST .../slack/install/byo?agent_id=…` 를 직접 호출합니다.
4. Patchbay는 저장 전에 쌍을 검증합니다.
   - Bot token은 `xoxb-` 로 시작하고 실시간 `auth.test` 를 통과해야 합니다(team id와 Bot user id도 여기서 얻습니다).
   - App-level Token은 `xapp-` 로 시작하고 app id를 파싱할 수 있으며 실시간 `apps.connections.open` 을 통과해야 합니다. 이벤트를 영원히 받을 수 없는 token은 저장되지 않습니다.
   - 두 token이 같은 Slack app의 것이어야 합니다(`auth.test` 가 반환한 bot id로 `bots.info` 를 조회해 대조합니다). 맞지 않는 쌍은 깨진 채로 연결하지 않고 `400` 으로 거부됩니다.
5. Bot은 에이전트당 하나입니다. 설치 행은 workspace + 에이전트 단위로 관리되며, 같은 에이전트의 재연결은 해당 행을 덮어씁니다. 다른 에이전트나 workspace에 이미 연결된 Slack app은 `409` 로 거부됩니다. 원래 연결을 먼저 해제한 뒤 다시 연결하세요(소속 에이전트가 보관된 상태라면 복원하거나 해당 Bot을 해제하세요).

## 2. 매니지드 OAuth 콜백 안내

Go 백엔드에는 BYO와 별도로 호스트형(매니지드) OAuth 서비스가 포함되어 있습니다(`server/internal/integrations/slack/managed_oauth.go`). 일회용·10분 유효·해시 저장 방식의 설치 state를 발급하고(DB에 닿는 것은 state 해시뿐입니다), 콜백 code를 `https://slack.com/api/oauth.v2.access` 에서 교환합니다. 설치자가 방문하는 주소는 `https://slack.com/oauth/v2/authorize` 이며, scope는 `ManagedSlackBotScopes` (`app_mentions:read,channels:history,chat:write,commands,files:read,groups:history,im:history,mpim:history,reactions:write,users:read`)입니다. 매니지드 클라이언트 자격 증명이 없으면 교환이 어중간하게 동작하지 않고 명시적으로 실패합니다.

자체 호스팅 배포는 BYO 경로를 그대로 사용하므로 OAuth 콜백 설정이 필요 없습니다. Go 서버의 매니지드 begin / callback 라우트는 호스팅 클라이언트 자격 증명(`PATCHBAY_SLACK_CLIENT_ID/_SECRET`) 없이는 동작하지 않습니다. BYO 설치 자체에는 OAuth code 교환이 없습니다. 자체 호스팅용 설치의 app manifest에 Slack redirect URL을 추가하지 마세요. Socket Mode에는 필요 없습니다.

## 3. localhost 바인딩 경고

<Callout type="warning">
Docker Compose는 포트 `3000` 과 `8080` 을 `127.0.0.1` 에만 바인딩합니다. 공개를 위해 `0.0.0.0` 으로 바꾸지 마세요. 대신 HTTPS를 지원하는 리버스 프록시(예: Caddy)를 앞에 두고 `127.0.0.1:3000` / `127.0.0.1:8080` 으로 전달하세요. [자체 호스팅 빠른 시작](/self-host-quickstart#3-choose-how-to-access) 을 참조하세요.
</Callout>

메시징 링크가 동작하는지는 두 URL 설정에 달려 있습니다.

- 계정 연결 링크는 `PATCHBAY_APP_URL` 을 사용하고, 미설정 시 `FRONTEND_ORIGIN` 으로 폴백합니다. `PATCHBAY_PUBLIC_URL` (백엔드 / API용 URL)은 사용하지 않습니다. 모든 멤버가 접근할 수 있는 Patchbay 주소를 지정하고, loopback 주소는 피하세요.
- 자체 호스팅 환경에서는 `FRONTEND_ORIGIN` 을 공개 app origin으로 반드시 설정합니다. 초대 링크, cookie 속성, WebSocket origin 검사가 모두 여기서 파생됩니다.

연결 링크나 `/api/config` 의 `daemon_server_url` 가 여전히 `localhost` 라면 `.env` 에 로컬 기본값이 남아 있는 것입니다. `FRONTEND_ORIGIN` 과 `PATCHBAY_APP_URL` 을 공개 URL로 명시 설정한 뒤 `docker compose -f docker-compose.selfhost.yml up -d` 로 컨테이너를 다시 만드세요(`restart` 만으로는 `.env` 가 다시 읽히지 않습니다).

## 4. 자격 증명 취급

- `PATCHBAY_SLACK_SECRET_KEY` 는 Slack용 단일 배포 전체 키로, base64로 인코딩한 32바이트입니다.

  ```dotenv
  PATCHBAY_SLACK_SECRET_KEY=<base64로 인코딩한 32바이트 키>
  ```

  ```bash
  openssl rand -base64 32
  ```

  설치 서비스는 null이 아닌 암호화 box를 필수로 하며, 개발 환경에서도 평문 저장을 거부합니다. 이 키가 연동 전체의 전제 조건입니다. 없으면 Slack이 전혀 동작하지 않습니다.
- 두 token은 이 키로 암호화되어 설치 설정에 base64 암호문으로 저장됩니다(`xoxb-` 아웃바운드 token은 `bot_token_encrypted`, `xapp-` Socket Mode token은 `app_token_encrypted`). 평문으로 저장되는 일은 없습니다. 암호화된 Bot token은 API 응답에 의도적으로 포함하지 않고, 표시용 안전 항목(`app_id`, `team_id`, `bot_user_id`)만 반환합니다.
- 붙여넣은 token은 자격 증명으로 취급합니다. 태스크, 댓글, 리포지토리에 적지 마세요. 서버는 검증 전에 두 값의 앞뒤 공백을 제거합니다.
- 키는 장기간 보관하세요. 변경하거나 잃어버리면 저장된 token을 복호화할 수 없어 모든 Bot을 다시 연결해야 합니다.
- 계정 연결 token은 일회용이며 15분 뒤 만료됩니다. 교환할 때는 token 안의 신원이 아니라 세션의 Patchbay 사용자에게 Slack user id를 바인딩합니다. 교환할 수 있는 사람은 workspace 멤버뿐입니다. Bot에게 다시 메시지를 보내면 새 링크가 발급됩니다.
