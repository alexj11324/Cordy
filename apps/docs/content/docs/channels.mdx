Chat integrations let the team ask an agent questions, @-mention it in a group chat, or create issues from the chat window — without opening Patchbay.

Personal WeChat, Feishu/Lark, Slack, DingTalk, WeCom, and Telegram are supported today. They share the same session, identity, and execution mechanics but install differently.

Personal WeChat uses Tencent's official iLink QR authorization. It works with an individual WeChat account and does not require a company, Official Account, WeCom organization, or developer AppID. The current adapter supports direct text conversations; group and media support are intentionally not advertised until the upstream protocol exposes a stable contract for them.

## Choose a platform

| | Personal WeChat | Feishu / Lark | Slack | DingTalk | WeCom | Telegram |
|---|---|---|---|---|---|---|
| Installation | Scan Tencent's iLink QR code in Patchbay | Generate a QR code in Patchbay and authorize with Feishu | Create a Slack app and paste its tokens | Create an internal app and Stream robot, then paste AppKey/AppSecret | Create a long-connection smart bot, then paste Bot ID/Secret | Create a Bot with @BotFather, then paste its token |
| DM the agent | Supported | Supported | Supported | Supported | Supported | Supported |
| Groups or channels | Not currently advertised | Triggered by @-mentioning the Bot | Triggered by @-mentioning the Bot | Triggered by @-mentioning the Bot | Triggered by @-mentioning the Bot | Triggered by @-mentioning or replying to the Bot |
| Create issues | `/issue` message command | `/issue` message command | `/issue` slash command | `/issue` message command | `/issue` message command | `/issue` message command |
| Connection | iLink `getupdates` long polling | Platform long connection | Socket Mode | Stream mode | Platform long connection | `getUpdates` long polling |

New connections are currently open only for mainland-China Feishu; existing international Lark connections keep working and can still be managed.

Each Bot is bound to one Patchbay agent. To use several agents on the same chat platform, connect a separate Bot for each.

DingTalk, WeCom, and Telegram are [community-maintained](/community-maintained): they ship in every release, but carry no official support SLA. Report problems in [GitHub issues](https://github.com/alexj11324/Patchbay/issues).

WeCom handles text messages today. Voice, image, and file messages get a short reply explaining that, and are not passed to the agent.

Telegram accepts text and, when attachment storage is configured, supported inbound media. Unsupported media gets a short reply and is not passed to the agent.

## How a message is processed

1. Patchbay resolves the Bot to its workspace and agent.
2. In a group or channel, only messages that explicitly @-mention the Bot continue; DMs need no mention.
3. Patchbay verifies the sender's account binding and workspace membership.
4. The message joins an [agent chat](/chat) session, and a task is created.
5. The agent's reply goes back to the original DM or thread.

Channel messages that don't @-mention the Bot never trigger the agent and are not added to its conversation context.

Ordinary messages follow this flow. `/issue` is a command, not a chat turn: Patchbay posts the result back to the originating platform but does not add the command to Patchbay Chat. Slack's native slash command continues through its separate asynchronous issue-creation flow.

## Session isolation

- Feishu/Lark separates sessions by chat; later messages in the same chat continue the same session.
- Slack separates DMs by channel; in a channel, each thread holds its own session.
- DingTalk separates sessions by conversation; each DM or group continues its own session.
- WeCom separates sessions by chat; each DM or group chat continues its own session.
- Telegram separates sessions by chat; forum topics are isolated by topic.

Follow-ups in a channel still need a fresh @-mention. The agent only receives messages addressed to it — it never reads the whole channel history automatically.

## Account binding

The first time a member messages the Bot, they receive an account binding link. After signing in to Patchbay, the platform account is linked to their membership in the current workspace. The WeChat account that scans the installation QR code is linked automatically.

Patchbay only runs the agent after binding completes. Every message re-checks account binding and workspace membership; after leaving a workspace, the Bot can no longer be used to reach it.

<Callout type="info">
Account binding only confirms who the sender is. Other members on the chat platform are not automatically added to the Patchbay workspace.
</Callout>

## Manage connections

Workspace owners and admins can connect or disconnect Bots; for Personal WeChat and Feishu/Lark, connecting and disconnecting is also open to the agent's owner. Regular members can view connected integrations and use the agents they have access to.

After disconnecting, the Bot stops receiving new messages. Existing Patchbay conversations and run records are kept.

## Self-hosting

A self-hosted deployment must configure a 32-byte encryption key for each platform before Patchbay opens its connection entry point:

```dotenv
PATCHBAY_LARK_SECRET_KEY=<base64-encoded 32-byte key>
PATCHBAY_SLACK_SECRET_KEY=<base64-encoded 32-byte key>
PATCHBAY_DINGTALK_SECRET_KEY=<base64-encoded 32-byte key>
PATCHBAY_WECOM_SECRET_KEY=<base64-encoded 32-byte key>
PATCHBAY_TELEGRAM_SECRET_KEY=<base64-encoded 32-byte key>
PATCHBAY_WEIXIN_SECRET_KEY=<base64-encoded 32-byte key>
```

These keys encrypt stored Bot credentials and WeChat context tokens. See [Environment variables](/environment-variables) for how to generate and store them. Patchbay Cloud already has this configured.

For multi-replica WeCom deployments, configure Redis so the cross-replica outbound relay can route replies to the process that owns the bot WebSocket. A single replica can use the direct local path.
