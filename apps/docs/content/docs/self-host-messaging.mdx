Self-hosted IM is server-managed. The Patchbay app only displays the platforms
that the server enabled and their observed runtime state; it does not provide
credential fields, manifest upload, QR configuration, or an install button.

## Deployment contract

1. Give the deployment a public HTTPS app host and API host. Phones and IM
   providers must reach these domains; `localhost`, `.local`, LAN addresses,
   and private IPs are rejected for account binding.
2. Generate the operator template with the checked-in setup helper. This is
   the server-side equivalent of Multica's self-host installer; it is not an
   app-side credential form:

```bash
scripts/messaging-self-host-setup.sh init \
  --app-url https://app.example.com \
  --api-url https://api.example.com \
  --env-file .env.messaging
```

3. Fill the server-owned `PATCHBAY_MESSAGING_WORKSPACE_ID` and
   `PATCHBAY_MESSAGING_INSTALLER_USER_ID` in the generated secret file. Set
   `PATCHBAY_MESSAGING_BOOTSTRAP=true` only when you want the server to
   materialize installations from that file at boot. An optional
   `PATCHBAY_MESSAGING_AGENT_ID` scopes the installation to one Agent; leave it
   blank for a workspace-level installation.
4. Keep each provider credential in the server secret manager. Never paste it
   into the Patchbay app or commit it to `deploy/messaging/manifest.yaml`.
   Slack bootstrap requires the `xapp-`/`xoxb-` tokens plus the app, team, and
   bot-user ids; the other provider variable names are listed in the manifest
   and generated template.
5. Run the deployment probe before starting the gateway:

```bash
PATCHBAY_APP_URL=https://app.example.com \
PATCHBAY_PUBLIC_URL=https://api.example.com \
PATCHBAY_MESSAGING_MODE=server_configured \
  scripts/messaging-self-host-check.sh
```

The checked-in manifest documents the transport and bootstrap variable expected
for each provider:
Slack uses BYO Socket Mode; Telegram uses polling; WeChat uses Tencent's iLink
QR authorization followed by polling; Lark uses its long connection; DingTalk
uses Stream mode; and WeCom uses its WebSocket transport. For WeChat,
`PATCHBAY_WEIXIN_SECRET_KEY` is the at-rest encryption key, not a bot token—the
iLink bot token is generated by the QR authorization flow and stored server-side.
Self-hosted app mode is read-only, so WeChat QR authorization is a managed-
gateway operation; a self-hosted operator must keep WeChat disabled until a
server-side QR control plane is available rather than putting a token in the app.
The supervisor owns leases and reconnects, so multiple server replicas do not
consume the same stream concurrently.

## Slack manifest and token steps

The Slack app manifest is checked in at
[`deploy/messaging/slack-app-manifest.yaml`](https://github.com/alexj11324/Cordy/blob/main/deploy/messaging/slack-app-manifest.yaml).
Copy its YAML into **Slack API Apps → Create New App → From a manifest**, install
the app into the workspace, then generate an App-level token with
`connections:write`. Store the resulting `xoxb-` Bot token and `xapp-` App-level
token in the server's secret manager. The helper can print the manifest for a
terminal-only workflow without exposing any secrets:

```bash
scripts/messaging-self-host-setup.sh slack-manifest
```

Socket Mode is an outbound connection from the server to Slack, so no Slack
Request URL or OAuth callback points at the operator's computer. The Patchbay
app remains read-only in `server_configured` mode; the server deployment is the
authority for credentials and installation lifecycle.

<Callout type="warning">
Pure localhost self-hosting can still be used for the web app and local ACP,
but cross-device IM binding is disabled until a public HTTPS origin is
configured. Patchbay will never send a localhost URL in an IM message or QR code.
</Callout>

## Message storage and execution

Patchbay follows the Multica-style split: the server stores the workspace-scoped
IM session, the durable `chat_message` transcript, deduplication record, and
task linkage in PostgreSQL. A browser or phone only caches that server state.
The local computer stores provider-native agent sessions, worktrees, and
execution logs; it connects through the existing daemon WebSocket and is not
part of account binding.

When a computer is offline, the installation and transcript remain intact and
new work waits for an available runtime. Signing in on another computer does
not require rebinding an IM identity.

## Operator checks

- `/api/config` reports `mode: server_configured`, `setupWritable: false`, and
  only the enabled provider types.
- Installation writes from the app are rejected with
  `server_managed_integration`; hiding a control in the frontend is not the
  security boundary.
- A provider is shown as connected only after its supervisor lease/transport
  heartbeat is current. An installation row with desired status `installed`
  alone does not prove a live connection.
- Self-hosted transports do not consume Patchbay Cloud hosted IM quotas.
