Self-hosted deployments connect Slack through the bring-your-own-app (BYO) Socket Mode path: each agent gets its own Slack app, and Patchbay opens one Socket Mode connection per connected app. Patchbay Cloud needs no extra configuration; a self-hosted deployment must set the token encryption key and reachable public URLs first.

This page is the self-hosting companion to [Slack Bot integration](/slack-bot-integration) and [Chat integrations](/channels). For container setup and upgrades, see the [self-host quickstart](/self-host-quickstart); for the full variable reference, see [Environment variables](/environment-variables).

## How self-host Slack works

- Each Slack app maps to one Patchbay agent. To connect several agents, create a separate Slack app per agent.
- The Bot connects out to Slack over Socket Mode, so no public Request URL or OAuth Redirect URL is needed for BYO installs.
- Every installation carries its own app-level token (`xapp-`) and gets its own Socket Mode connection, authenticated with that token alone. The bot token (`xoxb-`) is only used for outbound Web API calls such as `chat.postMessage`.
- Inbound events are routed by the real Slack app id (`config->>'app_id'`, matched against the event's `api_app_id`), so several BYO apps — several agents — can coexist in one Slack workspace.

The management API surface is:

- `GET /api/workspaces/{id}/slack/installations` — list installations (member-visible).
- `POST /api/workspaces/{id}/slack/install/byo?agent_id=…` — connect a BYO app (owner/admin). Body: `{ "bot_token": "xoxb-…", "app_token": "xapp-…" }`.
- `DELETE /api/workspaces/{id}/slack/installations/{installationId}` — disconnect (owner/admin). The row is kept for audit; reconnecting flips it back to active.
- `POST /api/slack/binding/redeem` — bind a Slack user id to the signed-in Patchbay user from the "link your account" prompt.

Hosted-only (inert without `PATCHBAY_SLACK_CLIENT_ID/_SECRET`):

- `POST /api/workspaces/{id}/slack/install/managed` — start a managed-OAuth authorization (owner/admin). Body: `{ "redirect_url": "…" }`.
- `GET /api/integrations/slack/oauth/callback` — public Slack redirect landing; consumes the single-use state, exchanges the code, and 302s to the bound redirect URL.
- `POST /api/integrations/slack/events` — public managed Events API webhook (HMAC-signed; tenant-routed by app + team). Managed installs have no Socket Mode link: this is their only inbound, and the Supervisor parks their slot instead of dialing.
- `POST /api/integrations/slack/commands` — public managed slash-command webhook (same signature story; replay protection is the `trigger_id` claim, as there is no Socket Mode envelope).

## 1. BYO Socket Mode deployment

1. Set `PATCHBAY_SLACK_SECRET_KEY` (see [Credential handling](#4-credential-handling)) and restart the backend. Without it the Slack integration is disabled entirely.
2. Create one Slack app per agent from the manifest in [Slack Bot integration](/slack-bot-integration), install it to the Slack workspace, and copy the `xoxb-` bot token plus the `xapp-` app-level token (`connections:write` scope).
3. In Patchbay, open the agent's **Integrations** page and paste both tokens, or call `POST .../slack/install/byo?agent_id=…` directly.
4. Patchbay verifies the pair before persisting anything:
   - the bot token must start with `xoxb-` and pass a live `auth.test` check (which also yields the team id and the bot user id);
   - the app-level token must start with `xapp-`, embed a parseable app id, and pass a live `apps.connections.open` check so a token that can never receive events is never stored;
   - the two tokens must belong to the same Slack app (resolved via `bots.info` on the bot id from `auth.test`). A mismatched pair is rejected with `400` instead of connecting in a broken state.
5. One bot per agent: the installation row is keyed by workspace + agent. Re-connecting an agent updates its row in place. A Slack app already connected elsewhere is refused with `409` — disconnect it in the other agent or workspace first (or restore/disconnect it if its agent is archived).

## 2. Managed OAuth callback notes

The Go backend ships a hosted (managed) OAuth service alongside the BYO path (`server/internal/integrations/slack/managed_oauth.go`). It owns single-use, ten-minute, hash-stored install states — only the state hash reaches the database — and exchanges the callback code at `https://slack.com/api/oauth.v2.access`. The installer visits `https://slack.com/oauth/v2/authorize` with the `ManagedSlackBotScopes` scope set (`app_mentions:read,channels:history,chat:write,commands,files:read,groups:history,im:history,mpim:history,reactions:write,users:read`). Without managed client credentials the exchange refuses loudly instead of half-working.

Self-hosted deployments stay on the BYO path and configure no OAuth callback: the managed begin/callback routes exist in the Go server but stay inert without hosted client credentials (`PATCHBAY_SLACK_CLIENT_ID/_SECRET`), and the BYO install performs no OAuth code exchange at all. Do not add a Slack redirect URL to the app manifest for a self-hosted install; Socket Mode needs none.

## 3. localhost binding warning

<Callout type="warning">
Docker Compose binds ports `3000` and `8080` to `127.0.0.1` only. Do not switch the binding to `0.0.0.0` to expose the deployment; put a reverse proxy with HTTPS (for example Caddy) in front and forward to `127.0.0.1:3000` / `127.0.0.1:8080` instead. See the [self-host quickstart](/self-host-quickstart#3-choose-how-to-access).
</Callout>

Two URL settings decide whether messaging links work:

- Account binding links use `PATCHBAY_APP_URL`, falling back to `FRONTEND_ORIGIN` when unset — never `PATCHBAY_PUBLIC_URL` (the backend/API URL). It must point to a Patchbay address every member can reach, not a loopback address.
- `FRONTEND_ORIGIN` must be set to the public app origin on any self-hosted deployment; invitation links, cookie attributes, and WebSocket origin checks all derive from it.

If binding links or `/api/config`'s `daemon_server_url` still show a `localhost` address, `.env` still carries local defaults: set `FRONTEND_ORIGIN` and `PATCHBAY_APP_URL` to the public URLs explicitly and recreate the containers with `docker compose -f docker-compose.selfhost.yml up -d` (`restart` alone does not re-read `.env`).

## 4. Credential handling

- `PATCHBAY_SLACK_SECRET_KEY` is a base64-encoded 32-byte key and the single deployment-wide secret for Slack:

  ```dotenv
  PATCHBAY_SLACK_SECRET_KEY=<base64-encoded 32-byte key>
  ```

  ```bash
  openssl rand -base64 32
  ```

  The install service requires a non-nil encryption box and refuses plaintext token storage even in development. The key gates the whole integration: without it there is no Slack at all.
- Both tokens are encrypted at rest with that key and stored as base64-encoded ciphertext in the installation config (`bot_token_encrypted` for the `xoxb-` outbound token, `app_token_encrypted` for the `xapp-` Socket Mode token) — never as plaintext. The encrypted bot token is intentionally absent from API responses; only the display-safe fields (`app_id`, `team_id`, `bot_user_id`) are surfaced.
- Treat pasted tokens as credentials: never put them in issues, comments, or repositories. The server trims whitespace on both values before validation.
- Keep the key long-term. If it is rotated or lost, stored tokens can no longer be decrypted and every Bot must be reconnected.
- Account binding tokens are single-use and expire after 15 minutes; redemption binds the Slack user id to the Patchbay user from the session, never from the token. Only members of the workspace can redeem. Messaging the Bot again mints a fresh link.
