---
title: Self-hosted messaging
description: Configure Feishu, Slack, DingTalk, WeCom, Telegram, and Weixin on your own Orvilo server.
---

The server operator configures self-hosted messaging. In
`server_configured` mode, the Orvilo app shows connection status, permitted
routing controls, and account-binding flows. Credentials, provider
authorization, and disconnects are managed on the server.

This guide covers Feishu, Slack, DingTalk, WeCom, Telegram, and personal
Weixin. **Weixin currently supports text in private conversations only**;
group messages and media are not supported.

## 1. Prepare the deployment

Complete the [self-host quickstart](/self-host-quickstart), sign in, and create
a workspace. Run the commands below from the repository root on the server.
Use a checkout and backend image from the same release. The Weixin command
requires an image containing `/app/orvilo-messaging`; use
`make selfhost-build` when testing the current source checkout.

Configure public HTTPS origins in the deployment's existing `.env`:

```dotenv
FRONTEND_ORIGIN=https://app.example.com
ORVILO_APP_URL=https://app.example.com
ORVILO_PUBLIC_URL=https://api.example.com
```

Replace the example domains with your own. Phones and IM users must be able
to open the app origin. Keep the HTTPS proxy and WebSocket forwarding from
the quickstart; localhost and private addresses cannot be used for
cross-device account binding. The server needs outbound access to each
enabled provider.

Generate a separate messaging template:

```bash
scripts/messaging-self-host-setup.sh init \
  --app-url https://app.example.com \
  --api-url https://api.example.com \
  --env-file .env.messaging
```

The helper creates a file with mode `0600`. Fill it through your deployment's
secret manager or a server-side editor. Keep its permissions and do not
commit it. Retain the base `.env`; it contains the database and authentication
configuration used by Compose.

## 2. Choose the workspace and keys

Use the [Orvilo CLI](/cli) signed in to this deployment to find the full UUIDs:

```bash
orvilo --profile selfhost --server-url https://api.example.com login
orvilo --profile selfhost workspace list --output json
orvilo --profile selfhost workspace member list WORKSPACE_UUID --output json
```

Replace `WORKSPACE_UUID` with the selected workspace's `id`. In
`.env.messaging`, set `ORVILO_MESSAGING_WORKSPACE_ID` to that ID and
`ORVILO_MESSAGING_INSTALLER_USER_ID` to an owner/admin member's `user_id`,
not the membership record's `id`.

Leave `ORVILO_MESSAGING_AGENT_ID` empty for a workspace connection. To target
one Agent, set it to that Agent's full UUID from
`orvilo --profile selfhost --workspace-id WORKSPACE_UUID agent list --output json`.
The bootstrap template supplies one installation per provider for this scope.

Generate a separate encryption key for each provider you enable:

```bash
openssl rand -base64 32
```

Store it in that provider's `ORVILO_*_SECRET_KEY` field below. Reuse the
existing key when updating an installation; replacing it makes stored
credentials unreadable. Leave unused providers' keys and credentials empty.

After editing `.env.messaging`, export its assignments before running the
terminal checks below. Plain `source` does not export newly defined variables:

```bash
set -a
. ./.env.messaging
set +a
```

The provider inspection commands below use `curl` and `jq`. They display
provider identifiers, not token values.

## 3. Configure providers

### Slack

1. Run `scripts/messaging-self-host-setup.sh slack-manifest`. In
   [Slack API Apps](https://api.slack.com/apps), choose **Create New App → From
   a manifest** and paste that YAML.
2. Install the app to your Slack workspace. Copy its `xoxb-` Bot User OAuth
   Token to `SLACK_BOT_TOKEN`.
3. Under **Basic Information → App-Level Tokens**, generate an `xapp-` token
   with `connections:write` and store it as `SLACK_APP_TOKEN`. Keep Socket
   Mode enabled. Both tokens must belong to this app.
4. Set `ORVILO_SLACK_SECRET_KEY`. Reload `.env.messaging` as shown above, then
   inspect the Bot identity:

```bash
curl -fsS https://slack.com/api/auth.test \
  -H "Authorization: Bearer ${SLACK_BOT_TOKEN}" \
  | jq -e 'select(.ok == true) | {team_id, user_id}'
```

Set `SLACK_TEAM_ID` from `team_id` and `SLACK_BOT_USER_ID` from `user_id`.
`SLACK_APP_ID` can be copied from the app's Basic Information page; the
bootstrap can also derive it from the app-level token. The checked-in
manifest contains the message events and scopes used by Orvilo.
Self-hosted Slack uses outbound Socket Mode and needs no managed OAuth
client credentials or callback URL.

### Feishu

1. Open the [Feishu developer console](https://open.feishu.cn/app), create a
   custom app, and add the **Bot** capability. Copy its App ID and App Secret
   into `LARK_APP_ID` and `LARK_APP_SECRET`; set `LARK_REGION=feishu` and
   `ORVILO_LARK_SECRET_KEY`.
2. Grant application permissions `im:message.p2p_msg:readonly`,
   `im:message.group_at_msg:readonly`, and `im:message:send_as_bot` for private
   text and group mentions. See Feishu's
   [Bot setup steps](https://open.feishu.cn/document/develop-an-echo-bot/faq?lang=zh-CN).
3. Reload `.env.messaging`, then obtain this Bot's identity using its own
   application credentials:

```bash
LARK_TENANT_ACCESS_TOKEN="$(
  jq -n '{app_id: env.LARK_APP_ID, app_secret: env.LARK_APP_SECRET}' \
    | curl -fsS https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal \
        -H 'Content-Type: application/json' --data-binary @- \
    | jq -er 'select(.code == 0) | .tenant_access_token'
)"
curl -fsS https://open.feishu.cn/open-apis/bot/v3/info \
  -H "Authorization: Bearer ${LARK_TENANT_ACCESS_TOKEN}" \
  | jq -e 'select(.code == 0) | {bot_open_id: .bot.open_id}'
unset LARK_TENANT_ACCESS_TOKEN
```

Set `LARK_BOT_OPEN_ID` to the returned `bot_open_id`. `LARK_TENANT_KEY` and
`LARK_BOT_UNION_ID` are optional identity metadata when available.
After starting the backend in section 4, open **Events & Callbacks**, choose
**Receive events through a long connection**, and subscribe to
`im.message.receive_v1`. Feishu requires a running connection when saving
this choice. Publish the app with access for the intended members, then test
a private message. These steps describe mainland-China Feishu; the hosted
App's international Lark creation entry remains unavailable.

### DingTalk

1. In the [DingTalk developer console](https://open-dev.dingtalk.com), create
   an enterprise internal app, enable its robot, and choose **Stream Mode**
   for message delivery.
2. Enable robot message sending (`qyapi_robot_sendmsg`). Add
   `qyapi_chat_manage` for Bot/group information, and publish the app to the
   intended organization members.
3. Copy **Client ID / AppKey** to `DINGTALK_CLIENT_ID` and **Client Secret /
   AppSecret** to `DINGTALK_CLIENT_SECRET`. Set `ORVILO_DINGTALK_SECRET_KEY`.
   If the console gives a separate robot code, set `DINGTALK_ROBOT_CODE`;
   otherwise it defaults to the client ID.

### WeCom

1. In [WeCom Admin](https://work.weixin.qq.com/wework_admin/frame#apps),
   create or edit a smart bot and enable **API Mode → Long Connection**.
2. Copy its **BotID** to `WECOM_BOT_ID` and its long-connection **Secret** to
   `WECOM_SECRET`. This is the smart-bot Secret, not a webhook
   Token/EncodingAESKey or an application's CorpSecret.
3. Set `ORVILO_WECOM_SECRET_KEY`; `WECOM_BOT_NAME` is an optional display name.
   The server connects to `wss://openws.work.weixin.qq.com`. See the
   [official long-connection guide](https://developer.work.weixin.qq.com/document/path/101463).

### Telegram

1. Open the official [@BotFather](https://t.me/BotFather), send `/newbot`,
   and choose a name and username. Store the returned HTTP API token in
   `TELEGRAM_BOT_TOKEN` and set `ORVILO_TELEGRAM_SECRET_KEY`.
2. Reload `.env.messaging`, verify the Bot identity, and remove an existing
   webhook so Orvilo can use polling:

```bash
curl -fsS "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/getMe" \
  | jq -e 'select(.ok == true) | .result | {id, username}'
curl -fsS -X POST "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/deleteWebhook" \
  --data 'drop_pending_updates=false' \
  | jq -e 'select(.ok == true) | {ok, description}'
```

Set `TELEGRAM_BOT_USERNAME` to the returned username. Stop any other polling
consumer of this Bot before starting Orvilo. Telegram rejects simultaneous
webhooks or competing polling consumers.

### Weixin

Set `ORVILO_WEIXIN_SECRET_KEY` and the workspace/installer scope from section
2, then start the backend as described below. A personal WeChat account on
your phone is required; a WeCom organization or developer AppID is not.

Run the operator command on your server:

```bash
docker compose --env-file .env --env-file .env.messaging \
  -f docker-compose.selfhost.yml exec backend \
  /app/orvilo-messaging weixin-auth
```

Scan the terminal's QR code with WeChat and approve the authorization. If
Weixin asks for a verification code, enter it at the terminal prompt. Keep
the command running until it reports an installation ID. It uses the
backend's configured database and encryption key, handles supported regional
redirects, and writes the authorized iLink credentials encrypted into that
database. It does not print the Bot token.

The command is available only in `server_configured` mode. Non-secret
`--workspace-id`, `--installer-user-id`, and `--agent-id` flags override the
corresponding environment values. If the QR expires, rerun the command for
a new code. Ctrl-C cancels the attempt; closing input at the verification-code
prompt also cancels it.

The `WEIXIN_BOT_ID`, `WEIXIN_ILINK_USER_ID`, `WEIXIN_BOT_TOKEN`, and optional
`WEIXIN_BASE_URL` template fields support importing credentials an operator
already holds from an authorized iLink session. Leave them empty when using
`weixin-auth`; the command does not require this import or
`ORVILO_MESSAGING_BOOTSTRAP=true`. Importing variable names alone does not
authorize a WeChat account.

## 4. Load and check the server configuration

Set `ORVILO_MESSAGING_BOOTSTRAP=true` in `.env.messaging` to import the five
token/app-based provider configurations at startup. Keep it `false` when
only using Weixin's operator QR command. Reload the file and check the
deployment configuration:

```bash
set -a
. ./.env.messaging
set +a
scripts/messaging-self-host-setup.sh check
docker compose --env-file .env --env-file .env.messaging \
  -f docker-compose.selfhost.yml up -d backend frontend
```

Use both env files for subsequent Compose commands. The messaging file
overrides matching base values; preserve any existing provider credentials
and encryption keys you intend to keep. `up -d` recreates changed services;
`restart` does not reload their environment. The manifest at
`deploy/messaging/manifest.yaml` documents variable names; the server reads
the injected environment, not this YAML file.

`check` validates deployment settings, not provider authentication. Bootstrap
encrypts the supplied credentials and creates or updates installation rows.
An imported row alone does not prove the provider accepted the credentials
or that a transport is connected.

## 5. Verify a private conversation

1. Open **IM → View details** in the self-hosted app. Confirm the intended
   workspace/Agent connection and its observed runtime status. If it is not
   connected, inspect backend logs and the provider's app configuration.
2. From the provider, send the Bot a short text message. Follow any account
   binding link, sign in to this workspace, then send the text again.
3. Confirm the text reaches the Orvilo conversation and a reply returns to
   the provider. Agent execution also requires an available computer/runtime.
   For Weixin, perform this check in a private text conversation.

An operator can inspect service health without displaying credentials:

```bash
curl -fsS https://api.example.com/readyz
curl -fsS https://app.example.com/api/config | jq '.messaging'
docker compose --env-file .env --env-file .env.messaging \
  -f docker-compose.selfhost.yml logs --tail=100 backend
```

`/api/config` should report `mode: server_configured` and
`setupWritable: false`. The app's credential lifecycle endpoints reject
writes with `server_managed_integration`. Existing account binding and
permitted routing remain available. To pause all messaging, set
`ORVILO_MESSAGING_MODE=disabled` and recreate the backend. Setting
`ORVILO_MESSAGING_BOOTSTRAP=false` only stops imports; it does not disconnect
existing installations.

The server retains installation records, IM sessions, and transcripts in
PostgreSQL when a computer goes offline. Computers hold their agent sessions
and execution files. Signing in on another computer does not require
rebinding an IM identity. Self-hosted transports do not use Orvilo Cloud
hosted IM quotas.
