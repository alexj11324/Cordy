连接 GitHub 后，Patchbay 会镜像 pull request，并在 issue 详情中显示 PR 状态、改动规模、CI 结果和合并冲突。只有经鉴权的 task/run 登记，或工作区成员执行显式 Attach 后，PR 才会显示为该 issue 的产物。`PB-123` 只便于人搜索 GitHub，不会建立关联。

GitHub 集成只读取安装时授权的仓库，不会提交代码、评论或 status check。

自部署的 Patchbay 还可以并行连接自托管的 Forgejo、Gitea 或 GitLab 实例，获得同样的显式关联、合并转 Done 和 CI 展示，入口在 **设置 → 集成 → Git 代码托管**，详见[自托管 Git 代码托管](/vcs-integration)。Patchbay Cloud 不提供该入口。

## 连接 GitHub

工作区 owner 或 admin 可以完成连接：

1. 打开 **设置 → GitHub**。
2. 打开 GitHub 集成总开关。
3. 点击 **连接 GitHub**。
4. 在 GitHub 中选择账号或组织，并授权全部仓库或指定仓库。
5. 安装完成后回到 Patchbay。

连接状态会显示在同一页面。普通成员可以查看状态，但不能连接、断开或修改开关。

<Callout type="info">
**GitHub 连接**决定 Patchbay 从哪些仓库接收 PR 事件；**代码仓库**设置决定智能体执行任务时可以选择哪些仓库。两者用途不同，需要分别配置。
</Callout>

## 功能开关

**设置 → GitHub** 中有三个开关：

| 开关 | 作用 |
|---|---|
| GitHub 集成 | 总开关。关闭后，下面两项不再生效，但不会断开 GitHub App。 |
| PR 侧栏 | 在 issue 详情中显示关联的 pull request。 |
| Co-authored-by | 在智能体创建的 commit 中加入 `Co-authored-by: patchbay-agent <patchbay-agent@users.noreply.github.com>`。 |
| **PR 卡片 → CI 与可合并性** | 对每个关联的 PR，Patchbay 从 GitHub API 拉取一份经鉴权的快照，把它的 **CI 状态**和**可合并性**镜像到卡片上（见下方 **PR 卡片展示什么**）。 |



## 让 PR 关联到 issue

规范路径是显式操作：智能体在经鉴权的 task/run 中创建 PR 后登记 Work Product，或工作区成员从 issue 中选择已镜像的产物并执行 Attach。也可以使用 CLI：

### 创建时直接挂上（CLI / 智能体）

```bash
patchbay issue pull-request attach PB-123 --url https://github.com/acme/api/pull/6
```

- issue 参数由当前工作区解析；URL 不能选择其他 workspace、task 或 run。
- 工作区成员的手工 URL Attach 在没有安装 GitHub App 时同样可用——侧栏至少显示 PR 编号和可点击的链接。
- task-scoped Attach 必须由已授权的 GitHub App 提供元数据，以便服务端验证精确的仓库和执行分支；调用者自填的标题、分支或 SHA 不能替代 ownership 证明。
- 已安装应用时，Patchbay 会通过应用 API 自动拉全元数据（标题、状态、分支、head），成员不需要额外参数。
- 可选参数（`--title`、`--state`、`--branch`、`--head-sha`）对应 `gh pr view --json` 的输出，仅供无应用时的成员手工 Attach 补充。
- 如果希望合并后移动 issue 到 Done，请加 `--close-intent`。PR 标题、正文、分支、commit 或评论中的文字都不会产生关闭意图。

所有显式路径都幂等，并汇聚到同一条 Work Product 关系。GitHub webhook 只镜像 provider 状态并刷新已有关系，不扫描 PR 文本，也不创建关联。task 结束时若尚未显式登记，服务端可以使用该 task 自己持久化的仓库身份、执行 workspace 和精确 head branch 做一次确定性查询；只有唯一匹配才会建立带审计来源的关系。零匹配保持未关联，多匹配、共享或仍被使用的分支、默认分支、detached HEAD 或查询失败会显示为歧义/不符合条件，等待有权限用户确认。即使 PR 文本包含 `PB-123`，没有显式 Attach 也仍然未关联。

## 在 issue 中查看 PR

关联成功后，PR 会出现在 issue 详情的 **Pull requests** 区块。每条记录会显示：

- 仓库、编号、标题和作者；
- `Open`、`Draft`、`Merged` 或 `Closed` 状态；
- 新增、删除行数和改动文件数；
- CI 状态：全部通过（带计数）、若干个失败（点名失败的 check），或若干个进行中；没有配置任何 check 的 PR 不显示这一项，"没有 check"不会被当成通过；
- 可合并性：可合并（仅当 GitHub 报告合并状态为 clean）、有冲突、blocked 或 behind。

CI 状态和可合并性来自 Patchbay 从 GitHub API 拉取的快照，两者互相独立；已合并或已关闭的 PR 不再显示这两项。GitHub 暂时不可用时，卡片会保留上一次的快照并标记为过期，而不是清空。

点击记录可以打开 GitHub 上的 PR。关闭 **PR 侧栏** 只会隐藏这个区块，不会断开连接。

## PR 合并转 Done 的条件

PR 合并不一定代表 issue 已完成。Patchbay 只有在以下条件同时成立时，才把 issue 改为 `Done`：

1. 至少一个已合并的显式关系启用了 `close_intent`；
2. 该 issue 没有其他仍为 `Open` 或 `Draft` 的工作 PR；
3. issue 当前不是 `done` 或 `cancelled`。

因此，在 PR 任意位置写 `PB-123` 都不会建立关联或触发完成。PR 关闭但没有合并，也不会完成 issue。

状态变化会以系统操作写入时间线，订阅该 issue 的成员会收到通知。

## 多个工作区

同一个 GitHub App installation 可以连接到多个 Patchbay 工作区。GitHub 事件会分别镜像到每个工作区，而每条显式关系都必须通过对应工作区的权限检查。工作区之间不会看到对方的 issue 或关系。

## 断开连接

在 **设置 → GitHub** 点击 **断开**，只会移除当前 Patchbay 工作区与该 installation 的关系，不会替你从 GitHub 卸载 App。已有 PR 记录会保留，新的事件不再进入该工作区。

撤销 GitHub 侧的仓库授权，需到个人或组织的 GitHub App installations 页面卸载或调整仓库范围。卸载后，与该 installation 关联的所有 Patchbay 工作区都会停止接收事件。

## 自托管配置

Patchbay Cloud 无需执行本节。自托管需要先创建自己的 GitHub App。

### 1. 创建 GitHub App

在 GitHub 的 **Developer settings → GitHub Apps** 中创建 App，并填写：

| 字段 | 值 |
|---|---|
| Homepage URL | Patchbay 前端地址，例如 `https://patchbay.example.com` |
| Callback URL | 留空 |
| Setup URL | `https://<api-host>/api/github/setup`，并启用 **Redirect on update** |
| Webhook URL | `https://<api-host>/api/webhooks/github` |
| Webhook secret | 一段长期保存的随机字符串 |

Repository permissions：

| 权限 | 级别 |
|---|---|
| Metadata | Read-only |
| Pull requests | Read-only |
| Checks | Read-only；用于显示 CI 状态 |
| Commit statuses | Read-only；用于汇总 legacy status 形式的 CI |

订阅以下事件：

- **Pull request**；
- **Check suite**、**Check run** 和 **Status**，用于触发 CI 与可合并性刷新。

如果不需要在 Patchbay 中显示 CI，可以不授予 Checks 和 Commit statuses 权限，也不订阅对应事件。

<Callout type="warning">
这里需要的是 **Webhook secret**，不是 OAuth Client secret。两边填写的 Webhook secret 不一致时，GitHub delivery 会返回 `401 invalid signature`。
</Callout>

### 2. 配置环境变量

从 App 的公开地址取得 slug。例如 `https://github.com/apps/patchbay-acme` 的 slug 是 `patchbay-acme`。

```dotenv
GITHUB_APP_SLUG=patchbay-acme
GITHUB_WEBHOOK_SECRET=<创建 App 时填写的 webhook secret>
FRONTEND_ORIGIN=https://patchbay.example.com
```

`GITHUB_APP_SLUG` 和 `GITHUB_WEBHOOK_SECRET` 缺少任意一个时，连接按钮会被禁用，webhook 接口也会拒绝处理事件。

下面两个变量是 PR 卡片显示 CI 状态与可合并性的必要条件——Patchbay 用它们以 App 身份鉴权并拉取快照：

```dotenv
GITHUB_APP_ID=<GitHub App 的数字 ID>
GITHUB_APP_PRIVATE_KEY=<完整 PEM 私钥，保留 BEGIN/END 行和换行>
```

私钥在 GitHub App 的 **Private keys → Generate a private key** 中生成。不配置时集成会平稳降级：PR 照常镜像，已有显式关系照常显示，只是 PR 卡片不显示 CI 或合并状态。

### 3. 更新数据库并连接

升级已有部署时，先执行常规数据库迁移：

```bash
make migrate-up
```

重启 API 服务，再到 **设置 → GitHub** 完成连接。

## 常见问题

- **连接按钮不可用**：检查 `GITHUB_APP_SLUG` 和 `GITHUB_WEBHOOK_SECRET` 是否已进入 API 进程。
- **Webhook 返回 401**：确认 GitHub App 与 API 使用同一个 Webhook secret，然后在 GitHub 的 **Recent Deliveries** 中重新投递。
- **PR 没有关联**：在 issue 中使用显式 Attach，或用 CLI 提交 PR URL。智能体运行则检查 execution provenance 和 discovery 状态；PR 文本中的编号不够建立关系。
- **运行结束后仍未关联**：零匹配、多匹配、共享/默认/detached 分支或 provider 查询失败需要有权限用户确认，task 详情会记录原因。
- **没有 CI 状态**：确认 `GITHUB_APP_ID` 和 `GITHUB_APP_PRIVATE_KEY` 已配置，App 具有 Checks 与 Commit statuses 的只读权限并订阅了对应事件。给已安装的 App 补加权限后，还需要各 installation 的所有者在 GitHub 上批准才会生效。
- **PR 合并后 issue 没完成**：确认显式关系启用了 `close_intent`，并检查是否还有其他关联 PR 处于 Open 或 Draft。
