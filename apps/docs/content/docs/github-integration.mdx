Once GitHub is connected, Patchbay mirrors pull requests and keeps their state,
change size, CI results, and merge conflicts visible in issue detail. A PR is
shown for an issue only after an authenticated task/run registers it or a
workspace member explicitly attaches it. An issue identifier such as `PB-123`
is useful for people searching GitHub, but it never establishes the relation.

The GitHub integration only reads the repositories authorized at install time; it never pushes commits, comments, or status checks.

Self-hosted Patchbay can also connect self-hosted Forgejo, Gitea, or GitLab instances in parallel, with the same explicit relation, merge-to-Done, and CI display. The entry point is **Settings → Integrations → Git hosting**; see [Self-hosted Git hosting](/vcs-integration). Patchbay Cloud does not offer this entry point.

## Connect GitHub

A workspace owner or admin can complete the connection:

1. Open **Settings → GitHub**.
2. Turn on the GitHub integration master switch.
3. Click **Connect GitHub**.
4. In GitHub, pick the account or organization and authorize all repositories or a chosen subset.
5. Return to Patchbay after the installation completes.

The connection status shows on the same page. Regular members can view the status but can't connect, disconnect, or change the switches.

<Callout type="info">
The **GitHub connection** decides which repositories Patchbay receives PR events from; the **code repositories** setting decides which repositories agents can pick when running tasks. They serve different purposes and are configured separately.
</Callout>

## Feature switches

**Settings → GitHub** has three switches:

| Switch | Effect |
|---|---|
| GitHub integration | Master switch. When off, the two below stop working, but the GitHub App stays connected. |
| PR sidebar | Shows linked pull requests in issue detail. |
| Co-authored-by | Adds `Co-authored-by: patchbay-agent <github@patchbay.ai>` to commits created by agents. |
| **PR card → CI & mergeability** | For each linked PR, Patchbay fetches an authenticated GitHub API snapshot and mirrors its **CI status** and **mergeability** onto the card (see **What the PR card shows** below). |



## Link a PR to an issue

The canonical relation is an explicit operation. When an agent creates a PR
inside an authenticated task/run, it can register the PR as that execution's
Work Product. A workspace member can attach an already mirrored Work Product
from the issue, or use the CLI:

### Attaching at creation time (CLI / agents)

```bash
patchbay issue pull-request attach PB-123 --url https://github.com/acme/api/pull/6
```

- The issue argument is resolved by the current workspace, and the attach is an explicit audited relation; the PR URL does not select a different workspace or task.
- A workspace member's manual URL Attach works without any GitHub App installation — the sidebar then shows at least the PR number and a clickable URL.
- A task-scoped Attach must have provider metadata from the authorized GitHub App so the server can verify the exact repository and execution branch. Caller-supplied title, branch, or SHA fields never replace that ownership proof.
- With an installation present, Patchbay pulls the full metadata (title, state, branch, head) through the App API itself; members don't need `--url` extras.
- Optional flags (`--title`, `--state`, `--branch`, `--head-sha`) accept what `gh pr view --json` prints for a manual member Attach when no installation exists.
- Add `--close-intent` when this explicit relation should move the issue to Done after the PR is merged. Text in the PR title, body, branch, commit, or comments never creates close intent.

All explicit paths are idempotent and converge on one Work Product relation
record. GitHub webhooks only mirror provider state and refresh an existing
relation; they never scan PR text or create an association. A task that ends
without explicit registration may perform one deterministic lookup using its
own persisted repository identity, execution workspace, and exact head branch.
Only one exact GitHub PR match is attachable. Zero matches remain
unassociated; multiple matches, a shared/active branch, default branch,
detached head, or an unavailable lookup remain visibly ambiguous or ineligible
for human confirmation. The branch is used for this first lookup only and is
not a durable relation key. A PR containing `PB-123` but lacking an explicit
attach is therefore still unassociated.

## View PRs on an issue

Once linked, PRs appear in the **Pull requests** block of issue detail. Each entry shows:

- repository, number, title, and author;
- `Open`, `Draft`, `Merged`, or `Closed` state;
- added and deleted lines and the number of changed files;
- CI status: all passed (with a count), some failed (naming the failing checks), or some in progress; PRs with no checks configured don't show this item — "no checks" is never treated as passing;
- mergeability: mergeable (only when GitHub reports a clean merge state), conflicting, blocked, or behind.

CI status and mergeability come from snapshots Patchbay pulls from the GitHub API, and the two are independent; merged or closed PRs no longer show either. When GitHub is temporarily unavailable, the card keeps the last snapshot and marks it stale instead of going blank.

Click an entry to open the PR on GitHub. Turning off the **PR sidebar** only hides this block; it doesn't disconnect anything.

## When a merged PR moves an issue to Done

A merged PR doesn't necessarily mean the issue is finished. Patchbay only moves an issue to `Done` when all of the following hold:

1. at least one explicit linked relation has `close_intent` enabled;
2. the issue has no other working PR still `Open` or `Draft`;
3. the issue is not currently `done` or `cancelled`.

Writing `PB-123` anywhere in a PR does not establish a link or trigger
completion. A PR closed without merging doesn't complete the issue either.

The status change is written to the timeline as a system action, and members subscribed to the issue are notified.

## Multiple workspaces

The same GitHub App installation can be connected to multiple Patchbay
workspaces. GitHub events mirror into each workspace separately, while every
explicit relation is checked against that workspace. Workspaces never see
each other's issues or relations.

## Disconnect

Clicking **Disconnect** in **Settings → GitHub** only removes the relationship between the current Patchbay workspace and the installation; it does not uninstall the App from GitHub for you. Existing PR records are kept, and new events stop flowing into that workspace.

To revoke repository authorization on the GitHub side, uninstall the App or adjust its repository scope from your personal or organization GitHub App installations page. After uninstalling, every Patchbay workspace linked to that installation stops receiving events.

## Self-hosting setup

Patchbay Cloud doesn't need this section. Self-hosting requires creating your own GitHub App first.

### 1. Create a GitHub App

Create the App under GitHub's **Developer settings → GitHub Apps** and fill in:

| Field | Value |
|---|---|
| Homepage URL | Your Patchbay frontend address, e.g. `https://patchbay.example.com` |
| Callback URL | Leave blank |
| Setup URL | `https://<api-host>/api/github/setup`, with **Redirect on update** enabled |
| Webhook URL | `https://<api-host>/api/webhooks/github` |
| Webhook secret | A random string you keep long-term |

Repository permissions:

| Permission | Level |
|---|---|
| Metadata | Read-only |
| Pull requests | Read-only |
| Checks | Read-only; used to show CI status |
| Commit statuses | Read-only; used to aggregate legacy-status CI |

Subscribe to these events:

- **Pull request**;
- **Check suite**, **Check run**, and **Status**, which trigger CI and mergeability refreshes.

If you don't need CI shown in Patchbay, you can skip the Checks and Commit statuses permissions and their events.

<Callout type="warning">
This is the **Webhook secret**, not the OAuth Client secret. If the two sides have different webhook secrets, GitHub deliveries return `401 invalid signature`.
</Callout>

### 2. Set environment variables

Take the slug from the App's public URL. For example, the slug of `https://github.com/apps/patchbay-acme` is `patchbay-acme`.

```dotenv
GITHUB_APP_SLUG=patchbay-acme
GITHUB_WEBHOOK_SECRET=<the webhook secret you entered when creating the App>
FRONTEND_ORIGIN=https://patchbay.example.com
```

If either `GITHUB_APP_SLUG` or `GITHUB_WEBHOOK_SECRET` is missing, the connect button is disabled and the webhook endpoint refuses to process events.

The next two variables are required for the PR card to show CI status and mergeability — Patchbay uses them to authenticate as the App and pull snapshots:

```dotenv
GITHUB_APP_ID=<the GitHub App's numeric ID>
GITHUB_APP_PRIVATE_KEY=<full PEM private key, keeping the BEGIN/END lines and newlines>
```

Generate the private key under the GitHub App's **Private keys → Generate a private key**. Without them the integration degrades gracefully: PRs still mirror and existing explicit relations still render — the PR card just shows no CI or merge state.

### 3. Update the database and connect

When upgrading an existing deployment, run the regular database migrations first:

```bash
make migrate-up
```

Restart the API server, then complete the connection in **Settings → GitHub**.

## Troubleshooting

- **Connect button disabled**: check that `GITHUB_APP_SLUG` and `GITHUB_WEBHOOK_SECRET` reached the API process.
- **Webhook returns 401**: confirm the GitHub App and the API use the same webhook secret, then redeliver from GitHub's **Recent Deliveries**.
- **PR not linked**: use the issue's explicit Attach action or CLI with the PR URL. For an agent run, inspect its execution provenance and discovery status; a matching identifier in PR text is not sufficient.
- **PR remains unassociated after a run**: zero matches, multiple matches, a shared/default/detached branch, or a provider lookup failure requires explicit human confirmation. The task detail records the reason.
- **No CI status**: confirm `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` are configured, and that the App has read-only Checks and Commit statuses permissions with the matching events subscribed. After adding permissions to an installed App, each installation's owner must also approve them on GitHub before they take effect.
- **Issue not completed after the PR merged**: confirm the explicit relation has `close_intent` enabled, and check whether other linked PRs are still Open or Draft.
