In day-to-day use of Orvilo you mainly deal with two kinds of credentials: browser sign-in sessions and personal access tokens. Browser sessions serve web and Desktop; personal access tokens serve the CLI, the daemon, scripts, and the API.

## Browser sign-in sessions

After signing in with an email verification code or Google, Orvilo stores a JWT in an HttpOnly cookie named `orvilo_auth`. The browser sends it automatically; JavaScript cannot read it directly.

Sessions last 30 days by default. Self-hosting admins can adjust the lifetime of sessions issued from then on with `AUTH_TOKEN_TTL`; see [Sign-in and signup configuration](/auth-setup#session-lifetime). Logging out clears the auth and CSRF cookies in the current browser.

Browser cookies are not meant to be copied into scripts or the CLI; use a personal access token to access Orvilo from a terminal.

## Personal access tokens

A personal access token (PAT) starts with `ovy_` and represents your account. It can access every workspace and API you have access to, so guard it like a password.

For CLI access, device login creates a 90-day PAT using the CLI client name. The **Authorized clients** page lists each client and lets you revoke its token. The full token is returned only to the CLI and saved in its profile; the web UI keeps only:

- the token's hash;
- the first few characters, for identification;
- the name, creation time, expiry, and last-used time.

The full value cannot be recovered. If you lose a CLI token, run `orvilo login` again to issue a new one; revoke the old client from **Authorized clients** if needed.

<Callout type="warning">
Don't put a PAT in repositories, issues, comments, screenshots, or logs, and don't pass it directly in shell commands that get saved.
</Callout>

## The CLI and PATs

When you run `orvilo login`, the CLI starts a device authorization request, prints a verification URL and one-time code, and waits while you approve it in a browser. The server then creates a PAT valid for 90 days and the CLI saves it to the current profile's config file:

```text
~/.orvilo/config.json
~/.orvilo/profiles/<name>/config.json
```

The daemon connects to Orvilo with the same PAT. A `ovy_` PAT with an expiry renews automatically when less than 7 days remain, extending it to 90 days from that moment. A failed renewal leaves the token unchanged; once a token has expired or been revoked, run `orvilo login` again.

The same flow works on a machine without a browser: open the printed URL on another computer and enter the one-time code. If you already have a PAT, `--token` remains available:

```bash
orvilo login --token
```

## Using a PAT in API requests

Put the PAT in the `Authorization` header:

```bash
export ORVILO_TOKEN='ovy_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx'

curl https://api.aspectlylabs.com/api/me \
  -H "Authorization: Bearer $ORVILO_TOKEN"
```

Workspace-level API calls also need the workspace, as required by the endpoint:

```bash
curl https://api.aspectlylabs.com/api/issues \
  -H "Authorization: Bearer $ORVILO_TOKEN" \
  -H "X-Workspace-ID: $ORVILO_WORKSPACE_ID"
```

In scripts, take the token from a secret manager or a protected environment variable — never hardcode it. On self-hosted instances, replace the domain with your own public API address.

## Logging out and revocation

`orvilo auth logout` only deletes the PAT saved in the current CLI profile; logging out on the web only deletes the current browser's cookies. Neither revokes the personal access token on the server.

If a token may have leaked, revoke it immediately under **Settings → Authorized clients**. Once revoked, the PAT can never be used again, and any other machines and scripts that saved it lose access too.

## Temporary tokens for agent runs

When the daemon claims a task, the server creates a temporary token for that run, prefixed with `mat_`. It is bound to the current user, workspace, agent, and task, is valid for at most 24 hours, and is cleaned up when the task ends.

The daemon injects this temporary token into the AI coding tool instead of handing the user's PAT to the agent. Requests made by the agent are therefore recorded as agent actions, and the token can't be used to reach sensitive operations restricted to users or owners.

These tokens are created automatically by the server; users never need to save or manage them.

## Other machine credentials

The server also recognizes two credentials used in internal or managed scenarios:

| Prefix | Purpose | Managed by |
| --- | --- | --- |
| `mcn_` | Orvilo Cloud Node connections | Orvilo Cloud Fleet |
| `mdt_` | Workspace-scoped daemon authentication protocol | Internal server flows |

Regular Cloud, self-hosted, and Desktop installations never need to create them manually. The user-side CLI and daemon always use `ovy_` PATs; don't construct tokens with other prefixes yourself.
