Patchbay is a Rust backend and pnpm monorepo. The simplest way to start locally is `pnpm dev`; it prepares the environment, source-matched runtime, database, and migrations for the current checkout, then starts the complete Electron client, API, and browser login/share origin.

## Requirements

- Node.js 22
- pnpm 10.28.2
- Rust stable with Cargo (required on a dev runtime cache miss)
- Docker Engine/Desktop, or native PostgreSQL 15+
- Git; Make is an optional POSIX convenience

`pnpm dev` is cross-platform. `PATCHBAY_POSTGRES_RUNTIME=auto` selects Docker
only for the Compose-published `localhost:5432` endpoint; set `native` or
`docker` to resolve an intentional ambiguity.

Treat the root `package.json`, `server-rs/Cargo.toml`, `server-rs/Cargo.lock`, and CI workflows as the source of truth for versions and dependencies.

## First start

```bash
git clone https://github.com/patchbay-ai/patchbay.git
cd patchbay
pnpm dev
```

The primary checkout uses `.env`. If the file does not exist, `pnpm dev` creates it from `.env.example`, then starts the shared PostgreSQL instance, installs dependencies, runs migrations, and starts the API, browser login/share origin, and Electron client.

Default addresses:

```text
Desktop: Electron window with renderer hot reload
Browser/share/login origin: http://localhost:3000
API: http://localhost:8080
```

The fixed local verification code comes from the development configuration. Do not use a local `.env` for an internet-facing deployment.

## Developing in a worktree

The repository supports running the primary checkout and multiple worktrees at the same time. They share one PostgreSQL container but use separate databases and ports.

```bash
git worktree add ../patchbay-feature -b feat/my-change main
cd ../patchbay-feature
make setup-worktree
make start-worktree
```

`make setup-worktree` generates `.env.worktree`; the database name and ports are derived from the path. To start it again:

```bash
make start-worktree
```

To stop Desktop/Electron, Web, and API for the current worktree:

```bash
make stop-worktree
```

You may also run `make dev` directly. The script detects a worktree through its `.git` file and selects `.env.worktree`.

<Callout type="info">
  Different worktrees share the PostgreSQL container, not the database. Do not
  start a new Compose project for every worktree. Check `POSTGRES_DB`, `PORT`,
  and `FRONTEND_PORT` in `.env.worktree` first.
</Callout>

## Common commands

### Full workflow

```bash
make dev              # Complete Electron + dev CLI + backend + Web origin + isolated DB
make start            # Same complete stack using the existing environment
make stop             # Stop the tracked Electron/backend/Web process tree for this checkout
make check            # Run the complete local verification workflow
make build            # Build the server, CLI, and migrate binaries
```

### Frontend

```bash
pnpm install
pnpm dev              # Complete Desktop development with renderer hot reload
pnpm dev:doctor       # CLI/backend/DB/agent/integration diagnostics
pnpm dev:web:next     # Next.js web client
pnpm build
pnpm typecheck
pnpm lint
pnpm test
```

There is one complete Desktop development path:

| Situation                                                                      | Command                                   | Work performed                                                                                        |
| ------------------------------------------------------------------------------ | ----------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Normal local product development                                               | `pnpm dev` or `make dev`                  | Electron, source-matched dev CLI, backend, Web origin, isolated DB, hot reload, and capability checks |
| Repeat development diagnostics                                                 | `pnpm dev:doctor`                         | CLI/source/version, backend/DB, agent discovery, Telegram/Weixin configuration                        |
| Frontend/Electron compile check                                                | `pnpm --filter @patchbay/desktop build`   | Production JS bundles; no Rust                                                                        |
| Validate an installer, signing/notarization, updater, embedded CLI, or release | `pnpm --filter @patchbay/desktop package` | Release Rust CLI and installer packaging; may take tens of minutes                                    |

The dev runtime cache holds the matching CLI, backend, and migration runner and
is keyed by Rust source, Cargo metadata, toolchain, target, architecture,
profile, and build variables. Cache hits do not compile Rust; misses build all
three together with the incremental dev profile and optional shared sccache. Worktrees
never share `node_modules` link trees, `server-rs/target`, databases, ports, env,
or processes. Release/package is separate and never reads the dev cache.

Root commands exclude Mobile by default. Mobile has separate scripts and CI; read `apps/mobile/AGENTS.md` before changing it.

### Backend

```bash
make server
make daemon
make test
make migrate-up
make migrate-down
make rust-build
```

To run a CLI command from source:

```bash
make cli ARGS="issue list"
```

## Changing frontend features

Place features needed by both Web and Desktop according to responsibility:

1. Put API types, queries, mutations, and platform-independent logic in `packages/core/`.
2. Put foundational UI in `packages/ui/`; it must not depend on business code.
3. Put business pages and components in `packages/views/`.
4. Keep Next.js, Electron, and routing adapters in the corresponding app.
5. Wire shared pages into both Web and Desktop.

TanStack Query owns server data. Zustand owns client state such as filters, drafts, and layout. See [Project architecture](/developers/architecture) and the root `AGENTS.md` for the exact boundary.

When adding or changing an API, update the zod schema in `packages/core/api/` and add parsing tests for missing fields, unknown enum values, and malformed data.

## Changing the database

Migrations live in `migrations/`; production query modules live in `server-rs/crates/patchbay-db/src/queries/`.

1. Use the next unused numeric prefix and create both `.up.sql` and `.down.sql`.
2. Do not add database foreign keys, cascade deletes, or cascade updates. Enforce relationships and cleanup in the application layer.
3. Every new index must use `CREATE INDEX CONCURRENTLY` or `CREATE UNIQUE INDEX CONCURRENTLY`.
4. Put each concurrent index in a migration file containing only that statement.
5. Edit the relevant handwritten SQLx query module directly; the Rust path has no generated sqlc layer.
6. Run the closest `patchbay-db` test first, then `make test` for the locked Rust workspace.

Use an application transaction in the service layer when multiple writes must succeed or roll back together.

## Test locations

| Change                                 | Test location                                                                       |
| -------------------------------------- | ----------------------------------------------------------------------------------- |
| Shared business logic, queries, stores | `packages/core/*.test.ts`                                                           |
| Shared pages and components            | `packages/views/*.test.tsx`                                                         |
| Web or Desktop platform wiring         | Corresponding `apps/*` directory                                                    |
| End-to-end workflows                   | `e2e/*.spec.ts`                                                                     |
| Backend                                | `#[cfg(test)]` modules or `tests/*.rs` in the relevant `server-rs/crates/*` package |

Run the check closest to the change first, then expand the scope. For a Docs-only change:

```bash
pnpm --filter @patchbay/docs typecheck
```

For shared frontend changes:

```bash
pnpm typecheck
pnpm test
```

For backend changes:

```bash
make test
```

Before submitting:

```bash
make check
```

`make check` runs TypeScript checks, locked Rust workspace tests, and Playwright E2E. CI also builds and lints according to the changed scope and runs platform- or installer-specific tests.

## Resetting the current development database

When you need clean data, reset the database named by the **current checkout's environment file**:

```bash
make stop
make db-reset
make start
```

`make db-reset` drops and recreates the current `POSTGRES_DB` and refuses to connect to a remote database. Before running it, check `.env` or `.env.worktree` and confirm the target database.

## Before submitting

- Read the root `AGENTS.md` and relevant nested instructions.
- Change only the scope required by the task.
- Write code comments in English.
- Do not commit `.env`, tokens, build artifacts, or local paths.
- Use conventional commits such as `feat(scope)`, `fix(scope)`, or `docs`.
- Describe behavior changes and the verification commands actually run in the PR.
