When a piece of work needs an agent or team to run it, set the issue's executor. The executor reads the issue's description and discussion, does the work with its own configuration and skills, and writes progress and results back to the same issue. Set a workspace member as owner when a human should remain accountable, and set a member, agent, or team as reviewer when the result needs review.

When you only need the agent to handle one specific request without changing ownership, use an [@-mention in a comment](/mentioning-agents) instead.

## Set the executor and start a run

1. Open an issue and choose the **Executor** role.
2. Pick an agent or a team. Use the **Owner** and **Reviewer** controls independently when those roles are needed.
3. Review the executor about to start in the confirmation dialog.
4. Add a handoff note if needed, then choose **Start**.

![Executor confirmation dialog: add a handoff note, or choose not to start yet](/images/docs/assign-confirm-dialog.webp)

The handoff note applies to this run only — use it for scope, ordering, or what to focus on this time. Requirements that should hold long term belong in the issue, the project description, or the agent instructions.

When you set a team as executor, the team becomes the issue's executor and the team leader starts first. It decides whether to hand work to other members, following how the team operates. Members set as owner or reviewer are accountable humans and do not start a run by virtue of that role.

## Execution after setting an executor

Patchbay creates a [task](/tasks) for the executor agent. Once an online runtime claims the task, it invokes the AI coding tool on that machine; progress, comments, and results then appear in the issue.

If the runtime is temporarily offline, the task waits in the queue; a task is bound to its runtime and never moves to another machine.

While executing, the agent can:

- read the issue's description, fields, and comments;
- use its bound skills, MCP servers, and project context;
- read files, run commands, and make changes in its local working directory;
- post comments and update the issue status.

What it can actually do is still limited by the agent's configuration, the runtime environment, and your permission to run it.

During the run, the agent manages the issue's status by judging what its work changes: starting on the issue's own ask moves it to `in_progress` right away, delivery moves it to `in_review`, work continuing beyond the turn keeps it `in_progress`, and consultation or discussion leaves the status untouched — these actions appear under the agent's identity in the timeline. Task lifecycle and issue status are separate: a task completing does not by itself change the issue status.

When the executor is a [team](/teams), the same rule applies: Patchbay enqueues the leader, and dispatching members is not delivery — a dispatch turn leaves the parent issue `in_progress`, and the leader only moves it to `in_review` once the overall goal is met.

## Assign without starting

**Don't start yet** in the confirmation dialog saves the role change without creating a task for this run. Use it to settle the owner/executor/reviewer roles first and start once the background or dependencies are ready.

`backlog` doesn't start a run when an executor is set either. Execution only follows after you move the issue out of `backlog`, or ask the executor for something in a follow-up comment.

When the issue already has an agent or team executor, moving it out of `backlog` opens the same dialog: that status change is what starts the run, so it offers the same handoff note and the same **Don't start yet**, which moves the issue without waking the agent. The dialog appears for every target outside the `backlog`, `done`, and `cancelled` categories.

Only the `backlog` category works this way, and a [custom status](/issues#custom-statuses) in that category behaves identically. Issues already in `done` or `cancelled` still start a run immediately when their executor is set or changed to an agent.

## Executor permissions

Whether you can set an agent as executor is decided by its Access:

- **Only me**: only the agent's owner can run it;
- **Specific people**: the owner and the listed members can run it;
- **Entire workspace**: every workspace member can run it.

Workspace owners and admins can manage agents, but being able to see one doesn't mean being able to run it. The executor picker disables agents you can't run. See [Agents](/agents#permissions-and-access) for the full rules.

## Change or remove an issue role

Switching the executor to another agent starts a new run for the new executor; selecting a member in the owner or reviewer role records human responsibility and doesn't invoke an AI coding tool. Removing the executor doesn't create a task either.

<Callout type="warning">
Changing the owner, executor, reviewer, or issue status doesn't stop a run that has already started. To interrupt it, stop the corresponding task in the execution log.
</Callout>

## Use the CLI

```bash
patchbay issue update MUL-42 --executor "Agent name"
patchbay issue update MUL-42 --executor-id <agent-uuid> --no-start
patchbay issue update MUL-42 --owner "Member name" --reviewer "Reviewer name"
patchbay issue status MUL-42 in_progress --no-start
patchbay issue assign MUL-42 --unassign
```

In scripts, use the role-specific `--executor-id`, `--owner-id`, or `--reviewer-id` to avoid matching the wrong object with the same name. Look up UUIDs with `patchbay agent list --output json`, `patchbay team list --output json`, or `patchbay workspace member list --output json`.

Use `--no-start` when an executor change should not create a new task — for example, when the same agent is already handling the issue from another run. The same flag is available on `issue update` and `issue status`. Changing the owner or reviewer never starts a task by itself. If a flow changes the executor and status, pass `--no-start` to both commands; suppressing the executor-triggered run does not suppress a later status-triggered run.
