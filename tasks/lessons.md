## 验证共享 UI 必须走 Electron，不要在本地起 Next.js dev server

**日期**: 2026-09-11
**场景**: 改造 `packages/views/chat/` 的聊天面板

**纠正**: 用户明确要求「走 electron 编译验证，不允许在本地使用 nextjs 开发」。

**为什么**: 项目 `CLAUDE.md` 的 Verification 节已经写明 —— 「Shared UI changes must be visually accepted: **prefer Electron** (`make up C=desktop`)」。`packages/views` 是 web 与 desktop 共享的代码，Electron 才是首选验收客户端。我先起了 `next dev` 属于选错了验收通道。

**怎么做**:
- 验证 `packages/views` 的改动 → `pnpm --filter @orvilo/desktop typecheck` / `build`，或 `make up C=desktop`
- Next.js dev server 仅在 Electron 起不来、或 renderer 损坏时作为回退
- 报验收结论时必须说明**在哪个客户端看的**
- 注意 `make up` 需要 Docker（PostgreSQL）；Docker 未启动时用 Electron 自己的编译/类型检查路径，不要顺手退回 Next.js

## 这台机器的 `npm` 是 bun 的 alias，会重写 pnpm 配置

**日期**: 2026-09-11

**现象**: 运行 `npm install` 后，根 `package.json` 被改写 —— `pnpm.overrides` 被提到顶层，并凭空注入 `workspaces.catalog`。原因是 `npm` 被 alias 成 `bun`，而 `bun install` 会主动把 `pnpm-workspace.yaml` 的 catalog 迁移成 npm/bun 原生格式。

**怎么做**:
- 本仓库一律用 `pnpm add` / `pnpm install`，禁止在仓库内跑 `npm` / `bun install`
- 装完立即 `git diff package.json` 校验没被改写
- 依赖解析实验放到隔离目录外做，或用 CDN 直接读包，避免误触仓库

## pnpm 10 不再读取 package.json 的 `pnpm` 字段

**日期**: 2026-09-11

**现象**: `pnpm 10.28.2` 警告 `The "pnpm" field in package.json is no longer read`，导致 `pnpm.overrides` 与 `pnpm.onlyBuiltDependencies` **静默失效**。后者会让依赖的 `postinstall` 被拦截 —— `@lobehub/editor` 正是靠 postinstall 给 `lexical@0.42.0` 打补丁。

**怎么做**:
- 新增 build script 白名单要写进 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies`，不是 package.json
- 仓库现有的 `pnpm.overrides` 迁移属于独立问题，动它之前先确认影响面

**补充（2026-09-11，同日实测）**: 上面那条修法**已应用**，但**不足以保证 postinstall 真的执行** ——
`pnpm-workspace.yaml:61` 的 `onlyBuiltDependencies: ['@lobehub/editor']` 位置正确，而一次
`pnpm install` 仍然把它列进了 `Ignored build scripts` 横幅，且 patch 确实没打上。
**没有确认机制，所以不写机制**：当时安装跑在 `CI=true` 下（为绕过
`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` 不得不加），这是一个**候选**而非结论；
另一个可疑点在于 `node_modules` 此前由**另一个 pnpm store**（`~/.cache/codex-pnpm-store/v10`）
构建，而新 pnpm 默认 `~/Library/pnpm/store/v11`，`node_modules/.modules.yaml` 可能是旧状态。
值得注意的是矛盾之处：`.modules.yaml` 的 `ignoredBuilds` **只**记了 `msw`/`sharp`/
`electron-winstaller`/`unrs-resolver`，**没有** `@lobehub/editor`，可是它的脚本确实没跑。

**怎么做（补充）**:
- **装完必须校验 patch，不能只看警告横幅**。按 `@lobehub/editor` 自带
  `scripts/postinstall-lexical-patch.cjs` 里**硬编码的 sha256** 校验**全部 8 个**文件 ——
  `lexical` 的 `Lexical.{dev,prod}.{js,mjs}` 四个，加上 `@lexical/yjs` 的
  `LexicalYjs.{dev,prod}.{js,mjs}` 四个（脚本里两组 `PATCH_CONFIGS` 分别标着
  `packageName: 'lexical'` / `packageName: '@lexical/yjs'`）；不匹配就手动跑该脚本再校验。
  只查前四个会「看起来干净」却漏掉协同用的那一份。
  失败是**静默**的：只有一行 warning，而 `lexical` 未打补丁会让编辑器行为异常且难以归因。
- 该脚本用「临时文件 + rename」写，因此**不会**污染 pnpm store；store 里那份是未打补丁的，
  这既解释了为什么重装会退回未打补丁状态，也说明重跑脚本是安全且幂等的。

## 共享 dev 实例的状态，只能用「对称的逆操作」还原

**日期**: 2026-09-11

**现象**: 用户打开 Electron 应用，看到侧栏变深色、主区一片空白，报成回归。实际代码没问题 —— 是 subagent 的窄屏探针发了 `setViewportSize({width: 420})` 之后**没还原**，另外留下了 `.dark` class。我随后"还原"成 1440×900，那不是在还原，那是在覆盖之上再盖一层。

**原因**: 在 CDP 附着模式下，`page.setViewportSize()` 发的是 `Emulation.setDeviceMetricsOverride` —— 它装的是一个**覆盖层**，不是窗口尺寸。所以用另一个尺寸去"还原"，永远不知道自己有没有盖回原样。

**怎么做**:
- 撤销用逆操作：`client.send("Emulation.clearDeviceMetricsOverride")`；`.dark` 就 `classList.remove`，`color-scheme` 就 `removeProperty`
- 写在 `try/finally` 里，断言抛错时也要执行
- 改过共享状态（视口、主题、zoom）的探针，报告里要给出**还原后的实测值**，不是"我已还原"
- 同一条适用于一切共享实例：dev server、Electron renderer、数据库。用值去覆盖值不算还原

## 验收半径 ≠ 任务粒度；任务一旦报告就关闭

**日期**: 2026-09-11

**现象**: 用户看到 subagent 几分钟不动，怀疑任务拆得不够细。实际是它在跑第三遍全量 `@orvilo/views` 套件（5000+ 用例，单次数分钟）。而真实成本来自两处：**验收半径太大**（迭代中间跑全量），以及**我把它叫回来三次**（它 22:48 已交报告，之后我又追加五件事，每件都要重跑一遍验证）。

**关键判断**: 拆得**更细**会让它更慢 —— 5 个 tab 拆成 5 个任务就是 5 次全量。粒度不是瓶颈，半径才是。

**怎么做**:
- 迭代期只跑碰过的文件（`vitest run <path>`，秒级）；全量每轮**只在最后跑一次**；`typecheck` 在报告前跑
- 判"卡住"先看证据：`ps` 有高 CPU 的进程、报告文件 mtime 在动 → 是长命令，不是死锁。不要问"你还在吗"
- **任务在它报告的那一刻就关闭。** 之后发现的任何东西，走 review findings、新任务，或明确开新一轮 —— 绝不追加给一个还活着的 agent
- 截图：每个改动面浅色一张；深色/窄屏是主题与外壳的属性，每轮取一个代表面即可

## 补：上一条的探针集对 in-process teammate 不成立

**日期**: 2026-09-12

**现象**: 我重犯了「任务一旦报告就关闭」上面那条。一个 task reviewer 沉默 3 分钟，我追问一次无果，就判它死了、另派了一个。**原 reviewer 在被替代者启动之前就已完成**，只是报告还没送达；我在发现后停掉了替代者。代价：对一份 40 KB diff 的重复 opus 评审。

**为什么上一条的做法这次用不了**: 上一条说「`ps` 看高 CPU、看报告文件 mtime」。**in-process teammate 这两个探针都不存在** —— 它没有独立 PID，报告走 team 邮箱而不是文件。所以「没有进程、没有新文件」**不是**子 agent 已死的证据，那正是一个报告尚未送达的子 agent 的正常状态。可用的探针只有它的状态行（idle / running）和「追问已入队」这件事本身：**一个已被追问的 idle 子 agent 是 pending，不是 failed。**

**真正出错的地方是「把关于结果的原则当成了超时」**: 我的理由是「不返回裁决的 reviewer 不是闸门」—— 这话是对的，我自己也说过。但**关于结果的原则无法设定时限**：它告诉你缺失裁决的代价，不告诉你多长时间的缺失仍然只是「尚未送达」。当一条正确的原则在为一个破坏性动作（杀掉、替换、重试）辩护时，举证责任在那**个动作**的证据上，而沉默是最弱的一种证据。

**怎么做**: 替换一个子 agent 之前，等得比"感觉合理"更久一点；先找它自己的产物（写完的文件、入队的消息），找不到就再等一轮，而不是按分钟数判死。

## brief 里的清单，和核过的清单，在纸面上没有区别

**日期**: 2026-09-12

**现象**: 一晚之内三份 brief 的三份清单被同一把 `grep` 证伪，每次不到一分钟：

- Task 7 的 `action` 段说"四个里有**两个**在本任务范围内"——实际**零个**（那九个文件根本不渲染 `SettingsTab`）。同一句话在 Task 6/7/8/9 四份 brief 里都有，**只在 Task 8 是对的**，是从 Task 8 抄出去的。
- Task 9 的同一段同样错（它的两个 tab 确实渲染 `SettingsTab`，但都不传 `action`）。
- Task 10 说 `settings-page.test.tsx` 有"**两条**"死 `vi.mock` 桩——实际**三条**（21/25/28 行）；且漏了 `issue-statuses-tab.test.tsx`，它是唯一一个有自己的测试文件的死模块。

**为什么危险**: brief 存在的意义是让每个任务的要求只属于它自己。一段对某个任务成立、被抄给邻居的段落，**带着"要求"的权威把一个错误答案一起带过去了**——它会让人不去查，因为答案看上去已经给了。

**怎么做**:
- brief 里**每一个点名了集合的句子**（哪些文件、哪些 tab、几条、两个还是三个），在派发前用一条命令把集合重新推导一遍，而不是读它。`grep -rl` 通常就够
- 写完清单后，问一句"这条清单是谁、在哪、怎么数出来的"——如果答案是"从隔壁抄的"，它就不是清单，是传闻
- 同上适用：**关于「某测试为什么恒真」的解释，本身是一个待验证的 claim。** 变异测试只能证明断言*确实*不能失败，永远不能证明*为什么*——这两问的证据不同。一个错误的机制解释会被下一个任务照抄（这个 plan 里就发生了一次，从 `labels-tab` 抄进 `tokens-tab`，直到变异测试把它推翻）

## 并行的前提是别把「共享」当成「已知」

**日期**: 2026-09-12

**现象**: 我先写好一份 reviewer 的 dispatch（授权它用变异测试复测守卫强度），**然后**才把并发从 1 条开到 4 条。约 10:14，另一个 implementer 观察到 `slack-tab.tsx` 被改成 `throw e` → `return` 又还原，按纪律**没有回滚**（回滚别人刻意的状态变更本身是另一种危险），记下时间戳并上报。它做得完全正确，而**顺序是我搞反的**。

**为什么旧规则这次用不了**: 已有规则是「改共享工作树之前先声明窗口」。它预设**有可声明的对象**。四个 agent 在同一个 worktree 上**没有共享频道**——没有任何一次声明能传到那个正准备跑测试的 agent 耳朵里。所以那条规则在并行下**无法执行**，而「这次变异是我授权的」不等于「这次变异是可控的」。并发读者看到的仍然只是「一个红的测试 + 干净的树」，那正是 flake 的签名。

**怎么做**:
- **敏感度变异要么在低并发窗口做，要么在自己的 worktree 做 —— 绝不在共享树上做，也绝不只靠"声明"。**
- 把它和「全量套件」归为一类：**写共享状态的验证是"排期"的，不是"允许"的。** 一小时里出现两次，足以让它成为标准而不是两个事件。
- 变异跑不了时，诚实的退路是**读**：调用方的 `onConfirm`、rejection 有没有被 catch、wrapper 的 `onOk` 有没有把 promise 返回出去。然后在报告里写明**变异没有跑以及为什么** —— 一个具名的局限，好过一个被污染的结果。
- 判据仍是红集的**成员**而不是数量（见 `mutation-red-set-is-a-signature`）。

**同时记**: 编排自身的并发就是机器负载的来源。7a 报告「外部进程 load 46」，实测榜首是 `node`/`claude`/`python3` —— 是我们自己。所以「全量套件没跑到绿」这笔账有一半是自己的，而**安排那个安静窗口是 controller 的活，不是等机器自己闲下来**。

## 「确认发现」也可能是过时快照，而且证据越完整越难看出来

**日期**: 2026-09-12

**现象**: 一场 71 个 agent 的并发审计给出 34 条「对抗性证伪后仍成立」的确认发现。其中**至少有四条在写下的那一刻就已经过时** —— 因为我或其他 agent 正在并发地改那棵树。最典型的一条：审计断言 `packages/views/integrations/index.tsx` 没有桥、是一个未包裹的第二宿主，并附上了全仓 `LobeThemeBridge` 的 grep 结果和一份三宿主清单。**那段 grep 当时是真的**；我读它的两分钟前刚把桥加上，宿主是四个。

**原因**: 并发期产生的报告描述的是**它读取时的那棵树**，而报告不带时间戳，也不带「我读的是哪个 commit」。它引用的行号、grep 计数、宿主清单**当时全部为真**，所以它读起来不像猜测，像测量。**证据越完整，越难怀疑它已经过期** —— 完整本身就是可信度的伪装。

**怎么做**:
- 读任何并发期产生的报告，**先确认它引用的文件此刻是否还是那个样子**，再读它的结论
- 一条发现的 `verdict: confirmed` 只说明它对自己的证据成立，**不说明它对当前这棵树成立**
- 要引用一个文件的状态时，**写 commit hash**，不要写行号；`git log` 在你写句子的这段时间里也会变
- 作为报告的作者：**在报告里写明你读的是哪个 commit**，让读者能自己判断它有没有过期

## 写出一个最高级，就当场给它配一次 grep

**日期**: 2026-09-12

**现象**: 我把「`skills-tab` 丢失的是通往 Skills 库的**唯一入口**，整个 surface 不可达」写进了 plan 的全局约束、账本和四份 brief（共 8 个文件）。**实测是错的**：Skills 路由另有入口（`app-sidebar.tsx` 的 `configureNav`、`global-shortcuts.tsx` 的 `goSkills`）。真实的缺陷是**面板内掉了一颗按钮**。二十分钟后，我给另一个 brief 写新文本时又冒出「这两个 tab 正是用户开关后台服务的**唯一入口**」——同样的错，全新的句子，而当时我刚读完上一条的证据。

**原因**: 我是从一个**实测**（面板内 0 个 button）跳到一个**推断**（所以整个 surface 不可达）的，中间那步「这东西还有没有别的入口」从来没查过。**这不是记性问题，是形状问题**：写「唯一」「只有」「全都」「一定」这类词时，手是不停下来的。而且这个错误的传播方向和别的相反 —— 它不是「把话说得太满以求确定」，是**把严重性往上抬**。**警报会自己传播，而且传播时不需要证据**：一个真实的缺陷被包装成「功能失联」，于是它在每份文档里都读起来更该优先处理。

**怎么做**:
- **只要写出一个最高级，就当场给它配一次 grep；配不上就删掉那个词。** 成本是几秒，收益是不用再回头改 8 个文件
- 尤其是「唯一入口 / 不可达 / 没有别的路径」这类关于**可达性**的断言 —— 它们决定优先级，而且几乎从来没人验过
- 报告一个缺陷时，把「我实测到的」和「我由此推断的」分开写。严重性属于后者

## 转述只能传结论，不能传证据坐标

**日期**: 2026-09-12

**现象**: 我把一条发现转述给实现者时，附了两组测试文件的「真渲染行号」。**两组是互换的** —— 我标为 `slack-tab.test.tsx` 的那组实际是 `telegram-tab.test.tsx` 的。实现者没有照抄，它自己 grep，发现对不上并回报了我。同一天早些时候还有一次：我用 `grep -rn "<IntegrationsTab"` 建宿主清单，把两个**同名但是不同组件**的文件并成了一份「一个组件的三个宿主」，并把它写进了 fix dispatch 和两份 reviewer prompt。

**原因**: 一个 identifier、一个行号，**离开它所在的文件之后就没有任何东西托着它了**。在这个仓库里尤其危险，因为同名是常态：两个 `IntegrationsTab`、两个 `Modal` 家族、四个接受 `action` 的组件。而转述又发生在「我已经查过一遍」之后，此时**复查的动机最低** —— 新到的信息以确认的形状抵达。

**怎么做**:
- **凡是要写进长期文档的行号，必须自己 grep 一遍。** 转述传结论（「这三个套件真渲染这个组件」），不传坐标（「行 175、216、238」）
- 建宿主清单时**解析 import**，不要按名字 join：`grep -rn "<X"` 之后再对每个命中文件 `grep -n "import.*X"`
- 交给别人时给**解析结果**（文件 + import 路径），不给 identifier

## 解释「为什么成立」的那句话，本身也是一个断言 —— 而且它比结论更容易传播

**日期**: 2026-09-12

**现象**: 三件事同一形状。(a) 一份修复了「结论过宽」的更正，**引入了方向相反的新过度概括**（从「这些组件有测试覆盖」改成「没有任何套件真渲染它们」，而后者也是假的）。(b) 四份 brief 里都写着「eslint 完全看不见这类违规」，而仓库**有**这条规则（`import-x/no-extraneous-dependencies`）—— 那次全绿的原因是依赖**本来就被声明了**。(c) 六份 brief 加 plan 的约束 11 都在引用一条**从未被写下过**的裁决编号 R23。

**原因**: **理由是通用的，结论是局部的。** 一个结论只对它的位置负责，而一句「因为 X」会被原样搬到所有看起来相关的地方 —— 它读起来像元知识，不像待验证的断言。所以一条错误的理由，寿命比它所支撑的结论长得多，而且它删掉的是**别人去查的动力**：说「这里没有安全网」，就没人再检查安全网。

**怎么做**:
- 更正一条断言时，**用和原断言一样的标准去验证更正后的那句话** —— 尤其是当更正的方向是「反过来」时
- 写「因为……」之前，先问它是不是一个**可以被 grep 证伪的**陈述；如果是，就 grep 它
- 引用编号时**命名内容**（「`action` 陷阱」），编号只作附加线索。一个没有 referent 的编号会被复制进六份文档而不触发任何检查
