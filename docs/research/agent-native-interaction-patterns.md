# Agent-native interaction patterns for Cordy

Research date: 2026-09-05. Scope: first-party documentation from Linear, GitHub, and Cursor, retrieved through Exa. These are documented capabilities, not hands-on product verification or evidence of measured usability gains. Cordy proposals below are design inferences, not assertions about its current implementation.

## Documented patterns worth borrowing

| Pattern | Concrete documented behavior | Implication for Cordy |
| --- | --- | --- |
| Start from context the product already holds | Linear agent sessions receive issue details, comments, project context, and workspace/team guidance. Its repository-suggestion API ranks accessible repositories using issue/session/guidance context and can shorten the choices shown to a user. [Linear agent interaction](https://linear.app/developers/agent-interaction) | Carry the current task, attachments, workspace, and prior conversation into the request. Show inferred context as editable chips; do not ask the user to type it again. |
| Ask a concrete choice only when needed | Linear's `select` elicitation presents labeled options; users can answer in free text instead. Auth linking has a separate action UI. [Linear signals](https://linear.app/developers/agent-signals) | Questions should be typed UI objects: decision options, target picker, or account connection. Do not force every answer through a blank text field. |
| Preserve responsibility when delegating | Linear distinguishes human assignee from agent delegate. Delegated work remains in the human's My Issues view. [Agents in Linear](https://linear.app/docs/agents-in-linear) | Show who owns the outcome separately from which agent is working. Delegation should not hide a task from its owner. |
| Distinguish exploration from execution | Linear's coding-session docs say direct change requests start work, whereas investigate/research/plan requests scope the problem. Cursor Plan Mode researches, clarifies, produces an editable plan, then offers a build action; Cursor says direct Agent mode is appropriate for quick/familiar tasks. [Linear coding sessions](https://linear.app/docs/coding-sessions), [Cursor Plan Mode](https://cursor.com/docs/agent/plan-mode) | Make the agent's interpretation visible: investigating, proposing an approach, or executing. Use a compact plan decision when a choice matters; avoid a mandatory approval screen for every small task. |
| Continue context across surfaces | Copilot can start from an existing issue with optional extra guidance or from a prompt with pasted/dragged/uploaded images. Starting from Copilot Chat carries conversation context into the session. [Kick off a task](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task), [Managing sessions](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents) | A screenshot plus “fix this” can become an enriched task draft. Moving from chat to execution should preserve the conversation instead of requiring another task description. |
| Surface actionable progress | Linear separates pending, active, awaitingInput, error, complete, and stale sessions. Its semantic activities distinguish action, elicitation, response, and error; its evolving plan API is in technology preview. [Linear agent interaction](https://linear.app/developers/agent-interaction) | The primary UI should answer “working, needs me, failed, or ready to review?” Keep detailed logs available beneath that summary. |
| Let users steer without restarting | Copilot accepts follow-ups during a run, applying them after the current tool call. Stop preserves pushed commits. [Managing sessions](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents) | Keep a small steering input and an explicit stop control. Show whether a correction was received/applied and what work was preserved. |
| Deliver evidence with the result | Cursor cloud agents can attach screenshots, videos, and logs, and provide a remote desktop for direct testing. Linear coding sessions show diffs and, when captured, screenshots/recordings with review. [Cursor capabilities](https://cursor.com/docs/cloud-agent/capabilities), [Linear coding sessions](https://linear.app/docs/coding-sessions) | End on a result card: changed behavior, preview/artifact, checks performed, unresolved items, and a relevant next action. A final chat paragraph alone is insufficient for visual changes. |

## Recommended direction after the user's clarification

The user's preferred entry is **one sentence → understand/clarify → split into several tasks → visual plan**, with Linear's restraint and “less is more.” That shifts the primary design object from a task-creation form or a long chat transcript to a concise plan the agent creates with the user.

The strongest documented precedent is Linear's context-aware shortlisting plus optional choice elicitation. The sources establish session checklists, delegation, and agent progress; they do **not** establish that these products always turn a sentence into a task dependency graph. Automatic task decomposition and dependency presentation below are Cordy proposals.

## A proposed Cordy interaction sequence

1. **Capture intent:** accept a short sentence, screenshot, pasted link, or an existing task. Derive a draft title and use existing context. Present the context visibly and allow removing incorrect items.
2. **Resolve only consequential ambiguity:** inspect available context first. If a decision remains, ask one compact question with two or three meaningful options, a recommendation with a reason, and a free-text path. Repository/module names should come from real candidates.
3. **Produce a compact visual plan embedded in the conversation:** show the understood outcome and a handful of concrete task cards, ordered by real dependencies. Each card starts with a deliverable and can expand into acceptance criteria/context on demand; a permanent right-hand detail panel and full-page graph are explicitly rejected by the user. Use a simple list when sequential work is clear; use lanes or connecting lines only when they explain parallel work or dependencies. This is a proposed Cordy design, not a claim about the researched competitors.
4. **Let the user steer the plan:** users can choose an alternative, remove a task, combine tasks, or refine one card without rewriting the whole requirement. Expose uncertain assumptions near the affected task. Confirmed Cordy decision: confirmation creates the tasks without starting them; a separate Start action begins the authorized work.
5. **Track work through states:** emphasize working / needs your decision / ready to review / blocked. Preserve the same task cards as execution progresses. Keep plan changes, action history, and logs inspectable without making the user read a transcript to learn status.
6. **Review the deliverable:** offer the screenshot, runnable preview, document, or diff first, alongside what was verified. Let a user request a concrete revision on the artifact, then continue the same task.

Example: user drops a screenshot and writes “这里太复杂了.” Cordy inspects the associated page/task and asks “主要想简化哪一部分?” with “减少填写（推荐）”, “减少步骤”, and “调整信息布局”. After selection, it generates a concrete interaction proposal and preview. The user should not have to author a PRD just to get started. This example is a proposed design, not a documented feature of a competitor.

## Limits that should affect the design

- **Less typing does not mean guessing silently.** Linear's coding-session documentation explicitly says clear outcomes, scope, and constraints reduce ambiguity. Cordy should help derive those details and expose assumptions rather than promise that any vague request can run correctly. [Linear coding sessions](https://linear.app/docs/coding-sessions)
- **A displayed choice is not automatically a strict enum.** Linear permits free-text answers to dismiss an elicitation and emits selected options as normal prompt activities. A Cordy option UI must preserve the user's actual answer, not coerce an unrelated response into a selection. [Linear signals](https://linear.app/developers/agent-signals)
- **Context freshness is a real contract.** Copilot issue assignment snapshots the issue title/body/comments; later issue comments are not seen, and follow-ups must go to the PR. Cordy should expose where continuing instructions reach the active agent and avoid silently splitting conversations. [Kick off a task](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task)
- **Provider capabilities differ.** GitHub documents that live steering is unavailable for third-party coding agents. Cordy cannot promise identical stop/steer/artifact behavior for every provider without testing its actual adapter. [Managing sessions](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- **Artifact publication has visibility consequences.** Cursor's optional embedding in GitHub PR descriptions uses unauthenticated, unguessable artifact URLs because of GitHub's image proxy. Showing a preview in the app and publishing it to an external PR should have distinct visibility semantics. [Cursor capabilities](https://cursor.com/docs/cloud-agent/capabilities)

## How to evaluate a prototype

Use the same small task scenarios in the current flow and prototype: explain a screenshot problem, delegate an existing issue, resolve an ambiguous target, correct a running agent, and review a visual change. Observe user-authored characters, repeated context entry, number of decision interruptions, wrong assumptions caught before execution, and ability to identify the actual outcome from the result screen. These are proposed evaluation measures; no numerical improvement is claimed by this research.
